Read-only review, 19 Nov 2026. I changed no code, committed nothing, released nothing and restarted nothing. Evidence below is what I saw (with the route I saw it by); where I infer, I say so. Paths are relative to the repo root unless absolute. My file is [muse-wonder.md](/home/spheg/Documents/code/edit/docs/plans/2026-11-19-honest-council/muse-wonder.md); the brief is [brief.md](/home/spheg/Documents/code/edit/docs/plans/2026-11-19-honest-council/brief.md).

## Verdict in five sentences

**Keep the app, rewrite its middle: verdict (b) — rewrite specific subsystems on the same shell, and change the process at the same time.** Do not rewrite the whole app on a new architecture (c) and do not stop and use something else (d): the Rust engine, the Script→edit flow and the agent's craft are genuinely good and have produced real videos, and no off-the-shelf tool does this team's bodycam/true-crime pipeline. Also do not take (a) — "keep the architecture, just work differently" — because the architecture as it stands *is* the bug generator: footage that can come from five places, three separate "missing footage" machines, and a cloud call on almost every path mean the next JJ incident is already latent even if everyone is careful. Confidence about 70%: high that the middle must be rewritten, lower that my ordering/sizes are right. What would change my mind: two weeks of canary evidence (below) showing imports/exports surviving killed networks, sleeps and restarts on real footage without data loss on the *current* code — if that already passes, (a) is enough.

The one-line version for a tired person: **Edit does not need a new app; it needs one place where footage lives, one place where unfinished work lives, and a rule that missing never means deleted — enforced in code, not in diligence.**

### RC2 — "Missing" was allowed to mean "deleted", and the fix is pasted in three places (explains ~20%; it is the trust-killer)

The Wi-Fi incident, traced end to end (brief's case study):

**Claim 2.3 [saw].** On nightly-87, JJ's Wi-Fi dropped; the interview file failed with relay socket-closed, was retried at 1 and 5 min, then handed to him as *"Waiting for you: one file couldn't be downloaded"*; he pressed **"Go on without it"**, which *took the interview's 19 ranges out of the script* and laid out 2:44 of door footage for a 25-minute edit; he deleted the project (commit `6e1275e3`, 20 files, +422/−56). A follow-on the next day (`30a17052`, JJ's Scissors Attack, 6.3 GB/52 min, moov at end, 8.3 s GOP): excerpts failed on strict duration checks ("it runs 29.8 s, not 29.2 s" — a B-frame reorder artefact) and 2-minute keyframe timeouts, and again the dialog offered "I have a replacement" / "Go on without it". An earlier commit `268f4bc0` (Nov 4) had already patched this dialog once ("skips every file … in one answer") — i.e. the dangerous button had been touched before and stayed dangerous.

Root shape, in code terms: a *transient* fetch failure was classified as a *person-decision*, and the person's decision was implemented as *destructive edit of the script* (ranges removed) rather than *placeholder that preserves duration/topology*. Three design errors stacked: (1) error classification by surface wording, (2) asking the user to adjudicate infrastructure, (3) implementing "proceed" as deletion. Any one alone is survivable; together they convert a 60-second Wi-Fi blink into total work loss. That is why this incident matters beyond itself: it is the purest example of Edit's default under uncertainty being *do something irreversible and ask the human to carry the risk*.

**Claim 2.4 [saw] — The Nov 19 fix is correct in spirit and reveals the duplication.** `6e1275e3` + `30a17052` now: passing failures retry by themselves every 10 min (`waiting_on: "passing"` in [script.ts](/home/spheg/Documents/code/edit/app/apps/server/src/script.ts:1451), `PASSING_RETRY_MS` in [import_steps.ts](/home/spheg/Documents/code/edit/app/apps/server/src/import_steps.ts:61)); "go on without" keeps ranges as black cards of their length (`skipFootage` in [script.ts](/home/spheg/Documents/code/edit/app/apps/server/src/script.ts:111), `GONE_WITHOUT_NOTE`/`goneWithout` in [project.ts](/home/spheg/Documents/code/edit/app/apps/server/src/project.ts:313), layout at [script.ts](/home/spheg/Documents/code/edit/app/apps/server/src/script.ts:3366)); exports no longer fail on gone-without footage ([missing_media.ts](/home/spheg/Documents/code/edit/app/apps/server/src/missing_media.ts), [exports.ts](/home/spheg/Documents/code/edit/app/apps/server/src/exports.ts)). Good. But the *same concept* — "footage that didn't come in, retried by itself, waivable by the person, never silently dropped" — is now implemented **three times**: (a) edit imports in `script.ts` + `import_steps.ts` (`whyOf`, `NeedsPerson`, `RETRY_WAITS [60s, 5min]`, `PASSING_RETRY_MS 10min`); (b) Script-mode (Writer) in [writer/missing.ts](/home/spheg/Documents/code/edit/app/apps/server/src/writer/missing.ts) (`DELAYS_MS [1,5,15min] then hourly`, in-memory `due` Map + timer, `.missing-here` dot-file so only the importing Mac retries); (c) editor footage in [missing_media.ts](/home/spheg/Documents/code/edit/app/apps/server/src/missing_media.ts) (same delays copied, waiver persisted in a *separate* file `<home>/footage-gone-without.json`, `waived`/`missingOf`). Three backoff schedules, three persistence shapes, three "who may waive" rules. The next transient-failure bug will be fixed in one and live in the other two. [Inferred] This triple-implementation, not any single dialog, is the class: **every subsystem invents its own missing/retry/waive semantics, so correctness has to be re-proven per subsystem.**

**Claim 2.5 [saw] — How many other places have the same shape?** I searched for the pattern (transient → user prompt → destructive or divergent fallback). Direct analogues still present: `skip_footage` tool text in [edit_tools.ts](/home/spheg/Documents/code/edit/app/apps/server/src/edit_tools.ts:2091) still frames the choice to the agent (now safe because layout preserves cards — the *prompt* is fine, the old *semantics* are gone); [writer/parts.ts](/home/spheg/Documents/code/edit/app/apps/server/src/writer/parts.ts:30) `missing`/`skipped` splits recordings "out of the case until they're here" — safe only because `writer/missing.ts` rejoins; [clean_strips.ts](/home/spheg/Documents/code/edit/app/apps/server/src/clean_strips.ts) (via stability audit finding 2): one changed removal strip used to invalidate *every* overlay's identity and force re-renders — same shape, different domain: *local change, global destructive consequence, no diff*. And `whyOf` itself in [import_steps.ts](/home/spheg/Documents/code/edit/app/apps/server/src/import_steps.ts:120) classifies failures partly by regex over error *wording* (`PERSON`, `QUOTA`, `DRIVE_LIMIT` patterns) — necessary for outside text (Drive/yt-dlp), but fragile as a primary mechanism: any new error string defaults somewhere, and the default decides whether a human gets asked. The safe default must be "passing/retry, never ask, never delete"; today that default is a property of lists that must be maintained.

### RC3 — Unfinished work has one good table and several shadow ledgers (explains ~15%)

**Claim 2.6 [saw].** [jobs.ts](/home/spheg/Documents/code/edit/app/apps/server/src/jobs.ts:1) is one of the best things in the codebase: one table (`<home>/jobs.json`), written before each step, resumers that check outputs before redoing (HEAD on R2, file listed), `putOff` backoff for unpaid work (1 h ×6 then daily), `Gone` for truly-gone, one resumer (`resumeJobs` in [serve.ts](/home/spheg/Documents/code/edit/app/apps/server/src/serve.ts:555), plus `wakeWhatPasses` at line 579). Its header honestly records why: *"95 restarts in three days of logs, each dropping the export, smoothing or watch under way"* and four prior ledgers with different rules.

**Claim 2.7 [saw].** But it is not the only ledger. Writer missing-footage retries live in an **in-memory** `Map` + `setTimeout` (`writer/missing.ts:29-48`): a restart loses the schedule and rebuilds it by scanning scripts at `start()` — workable, but a second resumer with its own rules (hourly vs jobs' 10-min/hourly mix, `.missing-here` ownership). Editor waivers live in `footage-gone-without.json`, not in jobs or the project. Script import state lives partly in the job's `args` (`shownJob`, [script.ts](/home/spheg/Documents/code/edit/app/apps/server/src/script.ts:1643)). Cloud lock state lives in [cloud_projects.ts](/home/spheg/Documents/code/edit/app/apps/server/src/cloud_projects.ts) (`mayWrite`, `renewLock`, `offline` flag, 401 detection at line 185). Marc's report today still shows the seam: archive `given_up: cut short by 3 restarts` needing a manual *unstick*, while JJ shows a `case … given_up (stopped by Sphe)` beside running cases. Three definitions of idle/busy/sleep (audit finding 5: `awake.ts` didn't see effects/removals; `busy.ts` returned empty; updater rechecks separately) were partially unified into jobs, but "may sleep / may restart / may update" are still answered in more than one place (`busyWith`, `awake`, `serve.ts` stop path with `jobs.freeze()` + `plannedRestart`).

Why it breaks: restarts, sleeps and updates are the *normal* environment (laptops!), so any work whose resumption depends on in-memory timers, a second file, or a human pressing unstick will eventually strand. The team's phrase for this is "stuck" — the single most common failure word in the history I sampled.

[Inferred] Edit was designed cloud-first when disks filled (Oct 29 "everything on the cloud"), then pulled back local under pain (Nov 2–6, pieced proxies, native player) without ever re-deciding the *authority* question: for an in-work project, the Mac must be authoritative and the cloud a replica/backup/handoff; today both think they are, mediated by locks and retries. Most "mysterious" team bugs (revision conflicts: 25 on M4 + 25 on JJ in the audit; "another Mac saved"; synced copies resuming each other's imports — fixed Nov 18 `a0e76d76` after Sphe's Linux box took over two of JJ's imports) are authority bugs wearing different clothes.

## 3. Why the audits miss what the team hits

**Claim 3.1 [saw].** Audits (including the Nov 8 audit referenced throughout commit messages, the Nov 18 stability audit, and the nightly-readiness audits in transcripts) look at: code correctness by reading, unit tests (mocked boundaries), CI green-ness, and log *counts* after the fact. The team's failures come from: (1) *time* — jobs lasting minutes-to-hours across sleeps, restarts, updates; (2) *the real network* — 8 Mbit/s, DNS death, socket death mid-part, relay/Convex/R2 each failing differently; (3) *real footage* — 6.3 GB moov-at-end bodycam files, 8.3 s GOPs, B-frame reorder, non-interleaved AVIs, 53 GB/48-recording Drive cases; (4) *two Macs + authority* — locks, sync, takeover; (5) *the agent in the loop* — large plans, background removal/effects contending with foreground play/export; (6) *disk as a shared, finite resource* under all of the above at once. A code read cannot see (1)–(6) because each lives in the *interaction* — e.g. `whyOf` looks reasonable line-by-line; it only becomes dangerous composed with a dialog that deletes ranges and a user whose Wi-Fi just returned and who reasonably trusts the button's wording.

**Claim 3.2 [saw].** Tests prove the mocked world. `import_jobs.test.ts` sets retry waits to 0 and sleep to no-op: it proves state-machine logic, not timing behaviour under a 10-minute passing-retry on a sleeping laptop. Acceptance proves first-frame/scrub on synthetic sources, relay-less. Neither is a criticism of the tests — they are good at their layer — but *no layer* owned "kill the network at 40% of part 813 and assert nothing is lost and nobody is asked". `docs/dev.md` checklist item 6 *describes* that test; it is a human's pre-nightly chore, not a gate. Unsurprisingly, the bugs the team hits are precisely the un-owned layer.

**What method would have caught the Wi-Fi incident before JJ did?** Three cheap, specific things, in order of value:

1. **A fault-injection import test (half a day to build, minutes to run):** import a real-shaped file (multi-GB, moov-at-end, long GOP — keep one such fixture; `30a17052`'s MartyBlank file description is the spec), drop the network (or blackhole the relay/R2 host) mid-fetch, restore it, *restart the server mid-import*, then assert: (a) import completes or is still retrying by itself, (b) the person was never prompted, (c) script ranges == original ranges (count and durations), whatever was waived renders as black cards. The pre-fix code fails (b) and (c) loudly; the post-fix code should pass. Run it in CI on the Mac leg with the network actually toggled (or a proxy that drops), not mocked.
2. **A "no destructive fallback" static rule:** any code path that responds to a fetch/IO failure by *removing user content* (script blocks, clips, media, overlays) fails review unless it goes through the single missing-media module (RC2 fix) with placeholder semantics. Greppable: flag deletions of `blocks`/`clips`/`media` outside an explicit user-delete tool. This catches the *class* at review time, including future subsystems.
3. **Kenobi canary as a gate, not a favour:** the local-first plan already specifies it (old state seeded, long+short edits side by side, restart+sleep mid-work, low disk; gate: no ENOSPC, no duplicate paid sends, short edit not stuck behind long). Make nightly tagging *require* its log. The Nov 18 log shows canaries catching real things (joined/ ignoring the floor; a `.partial` never swept) — the method works when used; it just isn't load-bearing yet.

More generally: replace periodic "full audits" (broad code reads that return 4/10 lists, per Sphe) with **continuous canary + a standing fault suite + log-budget alerting** (e.g. nightly notes flag any WARN kind exceeding a count, any `given_up`, any person-prompt shown for a `passing` failure). Audits should then only be commissioned for *architecture* questions like this one, not bug hunts.

## 4. What to keep (must survive any rewrite)
