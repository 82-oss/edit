# Where Edit should keep footage

## Ranked conclusions

1. **Play active edits from local files. Keep the library in the cloud.** Give the editing Mac one complete, easy-to-seek copy of each recording or imported excerpt the cut needs. This is the *proxy*. If the original is small and seeks well, one file can do both jobs. Once Edit says the cut is ready, jumping to the last minute should work with Wi-Fi off. Keep full-quality originals in R2, the team's cloud file store. Bring originals or the needed stretches onto the Mac for export, text removal and other work that needs the detail.
2. **Sphe's storage concern rules out downloading every original and every proxy at import.** Two long edits ran together on his Mac. The three editors' reports list 71 distinct edits between them. The right unit for keeping footage is today's work on this disk. Opening Home, receiving a shared script or seeing a project on another Mac should cost almost no footage space.
3. **Keep Tauri, the desktop window that houses Edit's interface.** The normal Mac viewer already draws through the native engine. It shares its picture readers, drawing code and sound mixing with export. The expensive difference is often where those readers get the footage. Fix that first. Then use the Mac player in more places where it passes the same picture and sound checks. Keep the browser player for people using a browser.
4. **Use a shared Mac as an optional export worker if the laptops need it.** It could hold originals and finish large jobs near a large disk. Making every editor play through it would bring network speed, queues and one machine's availability back into every session. Keeping the current cloud player and fixing the worst bugs is a sound bridge for old projects. It leaves an editor's next jump competing with the network.

## Where the failures came from

- **Playback.** Long recordings can have a preview built a minute at a time. The server presents the pieces as one video stream. The Mac window also needs files it can seek directly. On Nov 17–18 it wrote 16 GB of local copies in 15 minutes. One minute near the end contained 955 MB because the copy started at the beginning of the recording. The corrected minute was 26 MB. Nightly-85 fixed how new pieces are copied. Later code also isolates old bad copies and checks available space. One local proxy removes the need for both representations on the normal Mac path. A different failure remains possible even with local media. Kenobi skipped 515 frames in 23 seconds during competing analysis and downloads. Playback still needs priority. ## How to keep disk use predictable

1. **Price the edit before fetching it.** List unique files for picture, sound and effects. Check which are already on this Mac. Show the additional space only when it affects the editor. Use recorded file sizes when available. For a new encode, estimate from source duration and check again as it writes. If an editor uses five minutes of a four-hour recording, prepare a complete file for that excerpt, with a little footage on either side for adjusting the cut. Keep its link to the original time. Fetch more if the cut grows. Let the editor start on a ready section while the other needed files arrive.
2. **Give each disk one spending limit.** Today's cache target is a quarter of free space plus existing cache, capped at 50 GB. Recent projects can stay over target, and the basic free-space floor is 1 GB. Keep the adaptive target as a starting point. Test a separate 10 GB reserve for the operating system, then reserve each real job's peak space on top. Count temporary downloads, both sides of a file conversion, simultaneous jobs, effect parts and the final file while its parts still exist. Check the destination disk separately. Count shared files once. Recheck before each large write. Recover reservations after a crash. A proposed reserve is a trial value, not a guarantee about macOS. [Disk rules](/home/spheg/Documents/code/edit/app/apps/server/src/storage.ts) · [Current cleanup](/home/spheg/Documents/code/edit/app/apps/server/src/cache_cleanup.ts)
3. **Give each active project only the space it needs next.** Protect files currently playing, uploading or being read by an agent or export. Share the remaining room across projects with waiting work. Drop obsolete and speculative output first, then verified working copies for finished projects, then the least recently used idle project. Keep paid results and original files until their cloud copies are verified. Never erase a person's source file or chosen export to make room. If even one needed stretch and its temporary files cannot fit, pause that job before writing. Say how many GB it needs, or offer an available working drive. An editor can keep working on the sections already prepared.
4. **Treat Done as permission to release local copies after backup.** Keep the project, timing, effects, fonts, paid results and references needed to recreate it. On reopening, restore the needed files first. Verify the file identity and contents before marking a backup or handoff complete. A teammate can open the edit on another Mac while seeing which media still need to arrive. Preserve Edit's existing rule about who may save the project. Local cleanup must never erase the last recoverable copy. The separate cloud deletion plan is still documented as a dry run. It identified a 16.2 GB file from someone's disk that could not be fetched again. A cloud backup promise needs an explicit retention rule for such files. [Existing cloud retention plan](/home/spheg/Documents/code/edit/docs/plans/2026-11-11-r2-cleanup.md)
5. **Use full quality only where the work calls for it.** Export already reuses local originals and can stage 30-second stretches at original quality. Keep that option for sparse cuts. If the original is already here, use it in place. If nearly all of it is needed and fits, fetch it once. Reuse the same file across projects. A low-quality preview must never silently become the export source. Keep background exports where they earn their space. JJ's measured 23.6-minute export took 5 minutes 54 seconds from scratch and 15–24 seconds with the parts ready. ## Player decision and rollout

First trial the disk rules and complete local files on a new project, with the existing window and existing export engine. Keep old projects readable through their current path. Convert them on use when there is room. Preserve their source identifiers and frame times. Avoid a one-time conversion of the library.

Then test where the Mac still switches to the web player, especially full screen, script mode and recovery after a drawing failure. Tauri puts a native picture underneath the web controls. The web player also uses shared drawing code through WebAssembly, which lets a browser run that code. The two paths still differ in how they read picture and sound, keep time and present a frame. A live player must respond to a jump immediately. An export must write every frame in order. Share the interpretation of the edit and the choice of source, while keeping those timing rules. [Window implementation](/home/spheg/Documents/code/edit/app/crates/edit-window/src/preview.rs) · [Shared picture reader](/home/spheg/Documents/code/edit/app/crates/edit-engine/src/render.rs:444) · [Web engine](/home/spheg/Documents/code/edit/app/crates/edit-wasm/src/lib.rs) · [Preview and fallback behavior](/home/spheg/Documents/code/edit/docs/preview.md)

Compare the same two long edits on the same Mac before and after the trial. Time import to first usable section, then to whole-cut readiness. Time the first play and jumps to twenty distant cuts, both with empty storage and after reopening. Count missed frames and sound gaps. Record peak disk use with both edits running, then repeat after sleep, a lost connection and a handoff. Once ready, require a full play and distant jumps without network reads for footage. Check export against original-quality frames at cuts, with subtitles, cleaned text, camera timestamps, blurs and sound. Retire the stitched stream and minute copies on the Mac path only after that comparison passes and the browser can still open older edits. A slower first import or a worse full-screen experience would be a real cost of the change.

## Open questions that could change the decision

- What are the largest *simultaneous* source, proxy and output sizes across an ordinary week on each editor's Mac? Measure actual files and shared space once, by disk. Record the low point in free space. The three development examples above give scale, not a team average.
- How often does a second editor actually take over the same edit, and how long until they can play it? Count a change in the Mac that saves an edit. Count script handoffs and review-link views separately. Frequent takeovers would strengthen the case for uploading a ready proxy early.
- How much time do people spend jumping around long unused recordings before they choose a cut? If this is common, test the delay to the first useful section against today's on-demand pieces. A single large download before any playback would be a regression.
- Could a shared worker finish the projects too large for a laptop sooner? Time a full handoff, including any upload, queue, export and delivery. Compare it with a local export to an attached drive. Choose it if that end-to-end time and reliability justify another machine.
